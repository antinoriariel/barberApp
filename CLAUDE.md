# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

"Navaja & Co.": a barbershop booking PWA in plain PHP 8.2+ (no framework, no build step, no linter; Composer is dev-only for PHPUnit). UI text and docs are in Spanish (rioplatense). Data lives in MySQL/MariaDB via PDO (`DB_DRIVER=db` in `.env`); with `DB_DRIVER=files` the models fall back to the hardcoded `data/*.php` (read-only, booking returns 503). Auth is DNI + password (Argon2id), with `/registro` (Argentine mobile phone, unique, normalized to 10 digits by `Support\Phone`; one account per browser and at most `security.register_max_ip_day` per IP/24 h, tracked in `device_registrations` via `Models\Registration`) and "Olvidé mi contraseña" = WhatsApp link (`support.*` config, `/recuperar` redirects there; no email/reset tokens, the admin sets a new password), DB-backed sessions and an `audit_log`. `users.email` is unused (kept only to not lose data). Demo accounts seeded from `data/users.php` use `auth.demo_password`; the list (admin, barber, two clients) is in `users.md`.

DB setup: create the `navaja` DB + credentials in `.env` (see README), then `php bin/migrate.php` and `php bin/seed.php` (both idempotent). Schema changes = new `database/migrations/NNN_*.sql`. The local `.env` uses root because the XAMPP MariaDB privilege tables are corrupt.

## Run

Requires PHP 8.2+ with the GD extension (bundled with XAMPP). Web root is `public/`:

```bash
php -S 0.0.0.0:8000 -t public public/router.php
```

`public/router.php` is required with the built-in server so dynamic routes (`/login`, `/manifest.webmanifest`, `/icon.png`) reach the front controller. Unauthenticated requests redirect to `/login`.

## Architecture

Request path: `public/index.php` → `app/bootstrap.php` (PSR-4-style autoload of `App\` → `app/`, helpers, session) → `Core\Router` using `config/routes.php` → Controller → Models → View. See `docs/arquitectura.md` for full detail.

- **Models** (`app/Models`) are the only boundary to the data source: each branches on `Database::enabled()` (PDO via `Core\Database`, prepared statements only) or falls back to `Core\Data::get('<name>')`. Keep public signatures identical in both modes. Booking rules (validation, transactions, anti double-booking) live in `Services\Booking`, exposed as JSON by `AppointmentController` (`/api/disponibilidad`, `/turnos`, `/turnos/cancelar`, `/turnos/reprogramar`; CSRF via `_csrf` or `X-CSRF-Token`).
- **Views** are plain PHP, layered `layouts/` → `pages/` → `screens/` → `components/`. Components receive everything via parameters (`partial('components/x', [...])`); they must not query models or read the session. Always escape data with `e()` (helpers in `app/Support/helpers.php`).
- **Single-page front end**: `ShellController::index` gathers all model data and renders every screen (`inicio`, `servicios`, `reservar`, `barberos`, `perfil`) into one page. `public/assets/js/navigation.js` toggles screens by URL hash. Each screen is `<section class="view" id="view-<name>" data-title data-skel hidden>`. Screens show instantly (the simulated skeleton delays in `navigation.js` are set to 0; raise them or swap in real fetches when an API exists).
- **JS**: ES modules, `main.js` only initializes the others.
- **Guided tour** ("modo guía"): `tour.js` walks the client through every feature with driver.js (vendored in `public/assets/vendor/driver/`, v1.3.1, MIT; the CSP forbids CDNs). Opens from any `[data-tour-start]` button (the `?` in `components/topbar.php`, "Guía de la app" in Perfil) and by itself on the first visit to Inicio (localStorage `navaja-tour`). Steps live in `STEPS` (`screen` + CSS selector); before each step it shows that screen with `navigation.js` `show()`, skips steps whose element is missing, and returns to the original screen on close. When adding/renaming a screen element, update its selector there. Styling: `css/components/tour.css`.
- **CSS**: one file per module; load order is defined in `config/app.php` → `assets.styles`. The UI is mobile first and single-layout: on PC it is shown as a centered phone-width column (`.app` max 480px). The old sidebar/desktop layout was archived in `docs/archivo/desktop.css` and is no longer loaded. The admin panel (`body.admin-page`, also `/su`) gets its look from `css/pages/admin-skin.css`, loaded after `admin.css`/`su.css`: red-and-black brick photo `img/fondo.jpg` fixed in `body::before` under an even dark veil (the photo is very saturated), smoked-glass (dark) / cream-glass (light) cards that redefine the tokens inside them, header text always light (it sits on the photo), brass accent `--brass` for icons/eyebrows/selection and red only for actions, Cormorant Garamond italic (`--serif`) for subtitles. Section tabs and KPI medallions use `icon()` (`ICON_PATHS` in helpers: `chart`, `calendar`, `hourglass`, `ticket`, `wallet`, `jar`, `receipt`, `users`, `razor`…; tab icons live in `components/admin-header.php`). The header seal reads "BarberShop · Panel" with the razor logo `img/C.png` applied as a CSS mask (`.admin-brand-logo`) so it takes the brass color.

- **Admin panel**: `GET /admin?fecha=YYYY-MM-DD` (`AdminController` + `Models\Dashboard` + `pages/admin.php`), for `users.is_admin = 1` and for barbers in the sections granted to them (see Roles; grant admin with `php bin/make-admin.php <dni> [--quitar]`). Revenue = sum of `price` of `done` appointments per day; compared with the previous day. Services are edited at `GET /admin/servicios` (`POST /admin/servicios/guardar` create/update, `/estado` hide/show; never deleted because appointments reference them; `Service::validate` holds the limits; duration stays editable because the schedule uses it, but is not shown to clients). Products (sold at the counter, shown in the Servicios → Productos tab) are edited on the same page (`POST /admin/productos/guardar`, `/admin/productos/estado`; `Models\Product`, table `products`, seeded with INSERT IGNORE from `data/products.php` so admin edits survive; hidden, never deleted). Appointments are closed from the panel (`POST /admin/turnos/estado`: `done` / `no_show`); if a barber marks another barber's booking as `done`, `Dashboard::mark` moves it to them (cuts count by `barber_id`) and stores "Reservado con <original>" in `appointments.notes`. Expenses (gasto + observación) are loaded at `GET /admin/egresos` (`POST /admin/egresos`, `/borrar`; `Models\Expense`) and subtracted from revenue in the day and month results. Extra income ("Ingreso extra": fecha, monto, categoría `Corte extra`/`Otros`, observación) is loaded at `GET /admin/ingresos` (`POST /admin/ingresos`, `/borrar`; `Models\Income`, table `incomes`) and added to those results (`Dashboard::finance` → `extra`).
- **Waiting games** (`components/arcade.php`, `arcade.js`, `js/games/*.js`, `config/games.php`): `POST /juegos/iniciar` opens a run in `game_sessions` (`Models\GameSession`) and returns a single-use token (only its sha256 is stored); `POST /juegos/fin` (game, run, score) closes it with the SERVER clock (time spent is never sent by the browser; capped at `max_session`), checks the score against the per-game limits (`max_score`, `rate`/`burst`, `step`; `GameSession::plausible`) and, if valid, updates `game_highscores` (`Models\GameScore`, best per user); it answers the top `ranking_size` (6), shown on the game over card (names = first name + surname initial, inserted with `textContent`). Implausible runs are stored as `rejected` and audited (`game_score_rejected`). Leaving mid-game sends the run with `sendBeacon` (CSRF in `_csrf`). Time per game is internal, never shown: `GameSession::timeSpent()` / `totals()`, `php bin/game-stats.php [dni]`. Both tables are HMAC-signed (`Services\Integrity`, key `APP_KEY` or auto-created `storage/integrity.key`; losing it invalidates the signatures): rows edited by hand in the DB are ignored. `POST /juegos/premio` (game, run) only rewards a closed valid run, once, using the stored score, with the user row locked (one prize per day).
- **Walk-in queue** ("tome su número"): a QR printed at the counter (`GET /admin/fila`, SVG from the dependency-free `ServicesQr`) points to `/fila?c=<queue.code>`; the client confirms with a POST and gets the next number of the day (`ModelsQueueTicket`, numbers restart daily). Inicio shows the number, who they are after and who is being served (`components/queue-ticket.php`, polled via `GET /api/fila` by `queue.js`); the center tab button opens the camera (`scanner.js`, `BarcodeDetector`; needs HTTPS or localhost, otherwise the phone camera app opens the same link). `Permissions-Policy` allows `camera=(self)` for this. The QR URL uses `APP_URL`, so set it to an address phones can reach.
- **Dead hour** ("Hora muerta", `GET /admin/hora-muerta`, section `hora-muerta`, grantable to barbers): the admin picks a % (`DeadHour::PERCENTS`) and a duration (`DeadHour::MINUTES`) and starts it now (`POST /admin/hora-muerta`; `/terminar` cuts it early; starting another replaces the running one). `Models\DeadHour`, table `dead_hours`. While it runs, clients see `components/dead-hour.php` (Inicio and Perfil) with a countdown (`js/countdown.js`, corrected by the server clock; `countdown_text()` renders the first value), and `Booking::place` applies the discount to bookings **for today** made during it and rejects any other day while it runs (`DeadHour::locksToday()`; Reservar only shows today and says why). While it runs, service prices (Servicios, "Lo más pedido", the Reservar summary and `/admin/servicios` with a countdown notice; never products) show the list price struck through plus the discounted one (`components/price.php`, `sale_price()`, `$salePct` from `ShellController`); when the countdown ends `countdown.js` adds `html.sale-over` and only the list price remains (`Appointment::insert` stores the discounted `price` and `appointments.discount_pct`). The page lists recent ones with how many bookings used them.
- **Barber hours**: weekly schedule per barber edited at `GET /admin/barberos` (`POST /admin/barberos/horario`; `Models\BarberHours`, table `barber_hours`). A weekday without a row means the full shop day (first slot → `booking.closing_time`). `Schedule::slots` and `Booking::place` only offer/accept a barber inside their window; only days with bookings (`Schedule::weekdayStatus() === 'open'`) are editable. The same page picks which weekdays the shop opens (`POST /admin/barberos/dias` → `Schedule::saveOpenWeekdays`, table `opening_hours`; `bin/seed.php` only fills missing days so it never overrides that choice); closing a day does not cancel its booked appointments, the page warns how many there are. The same page creates barbers (`POST /admin/barberos/nuevo`, multipart; `Barber::validate` / `Barber::create`, slug from the name) and changes or removes their photo (`POST /admin/barberos/foto`). `Services\BarberPhoto` re-encodes uploads with GD (JPG/PNG/WebP ≤ 5 MB → center-cropped 400×400 WebP) into `public/img/barberos/subidas/` (git-ignored, random suffix so caches refresh); it only ever deletes files there, never the repo illustrations. Each barber card has a Habilitado/Deshabilitado badge (`POST /admin/barberos/estado` → `Barber::setEnabled`, column `barbers.enabled`, independent of `active`): `Barber::all()` / `find()` (app, schedule, booking) skip disabled barbers, `Barber::team()` / `find($slug, true)` (panel, users, `/su`) include them; booked appointments are kept and the card warns how many remain.
- **Roles**: client (default), admin (`users.is_admin`) and barber (`users.barber_id` → `barbers.id`, `User::isBarber()`). Every barber gets "Mi semana" (`GET /admin/mi-semana`, `User::MY_WEEK`, not grantable, not for admins): only their own row of the weekly cuts table (`components/admin-week-table.php`, shared with `/admin/barberos`), and it is where they land. Beyond that, a barber enters the admin panel only in the sections the admin ticks for them (`users.panel_access`, comma list of `User::SECTIONS` keys; `User::canSee()` / `panelSections()` / `hasPanel()`); every `AdminController` action calls `requireSection('<key>')` (the catalog write actions call `requireCatalogEditor()`, the shop days/barber hours ones `requireHoursEditor()` and barber create/photo/enable `requireStaffEditor()`: barbers see Servicios and the Barberos page read-only), and the header only shows allowed tabs (pages pass `'sections' => $user->panelSections()`).
- **Superuser** (`GET /su`, `SuperController`): a single account outside `users`, logged in by typing `superuser` in the DNI field (`Models\Superuser`, table `superuser`; set/rotate the password with `php bin/superuser.php [password]`, no argument = random one printed once; rotating bumps `session_version` and kicks open su sessions; idle timeout `security.superuser_idle`). `Auth::isSuperuser()` (session key `su`), `Auth::user()` stays null for it; `/su` 404s for regular accounts. Lists every account with its browsers (`user_devices`: IP, user agent, first/last seen, written by `Services\Device::touch` from `Auth::user()` at most once a minute), last 3 `audit_log` actions (`UserActivity`, audit now stores `user_agent`), and can edit, set password, suspend, close sessions, delete with full history (`User::purge`), block IPs (`ip_bans`) and "Permaban" browsers (`device_bans`, keyed by sha256 of the `navaja_dev` cookie). `public/index.php` answers 403 to banned IPs/browsers before routing (`Models\Ban::blocks`). It never lets the superuser ban their own IP/browser; emergency unban: `php bin/superuser.php --desbloquear-todo`. Superuser actions are audited with `user_id` NULL and `su_*` events. The KPI tiles on `/su` are links: `?ver=en-linea` / `?ver=de-baja` filter the account list (`SuperController::VIEWS`). IP bans can be temporary (`Ban::DURATIONS`, `ip_bans.expires_at`) and both ban tables count rejected requests (`hits`, `last_hit_at`). Tabs `su` / `su-registros` / `su-seguridad` / `su-auditoria` live in `components/admin-header.php`. `GET /su/registros` = every sign-up (data, IP, browser, same-IP count) with Permaban / IP ban / "Liberar navegador" (`POST /su/registros/liberar`, sets `released_at`). `GET /su/auditoria` = full `audit_log` with filters, pagination and CSV export (`/su/auditoria/exportar`, `;` + BOM, formula-injection safe) via `Models\AuditLog`; `GET /su/seguridad` = 24 h alerts (brute-force IPs with 1-click temporary ban, targeted DNIs, accounts seen from many IPs, new browsers on existing accounts, superuser access log) and audit retention (`POST /su/auditoria/limpiar`, 90/180/365 days, itself audited). Actions pass `volver=seguridad|auditoria` to come back to that page. Note: `users` is `utf8mb4_unicode_ci` while the newer tables are `utf8mb4_general_ci`; joins on text columns need an explicit `COLLATE`.
- **Users** (`GET /admin/usuarios`, admin only, never grantable): create (`POST /admin/usuarios/guardar` without id), edit name/phone/role/sections (same with id; DNI is immutable), set password (`/clave`, revokes that account's sessions) suspend/reactivate (`/estado`, `users.active`; suspended accounts can't log in and `Auth::user()` returns null) and permanently delete (`/borrar`, only accounts with no history: `User::deletableIds()`/`User::delete()`). Barber profiles are never picked: `User::saveFromAdmin` creates one named after the account (`Barber::provision`: role "Barbero", 0 years, rating 0 → shown as "Nuevo"; reuses an inactive unlinked profile with the same name), renames it with the account, hides it when the role changes away or the account is suspended (warns about future bookings) and `Barber::retire`s it on delete. You can't demote/deactivate yourself or the last active admin. Front end: `admin-users.js`. Seed staff via `'admin' => true` / `'barber' => '<slug>'` in `data/users.php`; staff get no sample appointments. Test accounts: `users.md`.

## Security rules (see `docs/seguridad.md`)

- Every `<form method="post">` needs `<?= csrf_field() ?>` and its action starts with `$this->requireCsrf($request)`. Nothing that changes state goes over GET (logout is POST).
- Escape with `e()`; colors going into `style=""` go through `css_color()`. The CSP forbids inline scripts and external origins other than Google Fonts; widen it deliberately if needed.
- `Auth::attempt($dni, $password, $ip)` rate-limits via `Core\RateLimiter` (table `login_attempts`; files in `storage/ratelimit/` with the files driver) and always returns the same error for a bad DNI or password. Record notable events with `Audit::log()`. Never log passwords or tokens.
- Errors are logged, not shown, unless `APP_DEBUG=1`. Use `Response::error()` for error pages (`pages/error.php`).
- DB plan and status: `docs/plan-base-de-datos.md` (all phases done). Never interpolate input into SQL. Tests: `vendor/bin/phpunit` (separate `navaja_test` DB, auto-created). Backups: `php bin/backup.php`, verify with `php bin/restore-check.php`. New migrations start at 022 (two 002 files exist; 021 = `dead_hours` + `appointments.discount_pct`; 020 = `barbers.enabled`; 019 = `users.phone` (unique) + `device_registrations`; 018 = `game_sessions` + `game_highscores`; 017 = `appointments.notes`; 016 = temporary IP bans + ban hit counters + `audit_log` indexes; 015 = superuser, `user_devices`, `ip_bans`, `device_bans`, `audit_log.user_agent`; 014 = `users.active` + `users.panel_access`; 007 = barber `photo`, 008 = `appointment_services` for multi-service bookings, 009 = `queue_tickets`, 010 = `expenses.notes`, 011 = `barber_hours`, 012 = `products`, 013 = `incomes`).

## Gotchas

- **Service worker cache**: after changing any CSS/JS, bump `CACHE` in `public/sw.js`; new static files must also be added to its `SHELL` list. Pages are network-first and intentionally not precached (they depend on the session); `login.js` tells the worker to purge cached pages (`purge-pages`). `/api/*` is never cached.
- Every method/function carries a Spanish docblock explaining its logic; keep that when editing.
- Adding a CSS component: create `assets/css/components/<name>.css`, register it in `config/app.php` and in `SHELL` in `public/sw.js`.
- Adding a screen: new `screens/<name>.php`, include it in `pages/shell.php`, add a tab in `components/tabbar.php` (`data-tab="<name>"`), and fetch any new data in `ShellController::index`.
- Adding a route: method in a controller + view in `pages/` + entry in `config/routes.php`.
- Adding a service only requires editing `data/services.php`; barbers are added from `/admin/barberos` (or seeded from `data/barbers.php`), products from `/admin/servicios`.
- PWA manifest and PNG icons are generated at runtime (`PwaController`, `Services\IconGenerator` using GD).
